# The Gate 1 path, proven end to end on free CI

**Run:** https://github.com/aarohkandy/auros-base/actions/runs/35539867513 · `ubuntu-latest` · 2026-09-20

A Fedora bootc image derived from Universal Blue Aurora was built, turned into a bootable disk, and
**booted to a running system in QEMU with hardware acceleration, on a free GitHub runner.**

| Stage | Result | Measured |
|---|---|---|
| Derived image build | ✓ | ~60 s on a warm pull |
| `bootc container lint` | ✓ | seconds |
| `bootc-image-builder` → qcow2 | ✓ | **~7 min**, output **4.4 GB** |
| QEMU boot | ✓ | **acceleration: `kvm`**, markers at **~30 s** (3 polls × 10 s) |

Serial console reached `sysinit.target`, `basic.target`, `network.target`, `network-online.target`,
`ssh-access.target` and — notably — **`bootc-status-update.target`**, which is the mechanism check U1
reads to confirm a booted digest.

## What this proves, and what it does not

**Proven:** the pipeline works, on free infrastructure, with KVM. Every load-bearing CI assumption in
PLAN.md is now a measurement. Gates 1 and 2 need no infrastructure spend and no external host.

**Not proven, and not claimed:** this was a *minimal probe derivative* — one marker file — not
`auros-base:hardened`. **Gate 1 is not passed.** Gate 1 requires our hardened base, with its policy
modes, update agent and signing, to build and boot and pass the full matrix. That build is running
separately and has its own failures to work through.

The distinction matters: what was de-risked is the *path*. Everything specific to our image is still
ahead.

## Numbers the check matrix now budgets against

- **~7 minutes** per qcow2. The matrix builds the disk **once** and each hardware profile boots the same
  file (`run-boot.sh --qcow2`), so seven profiles cost one build plus seven boots, not seven builds.
- **4.4 GB** per qcow2, against 110 GB free — several profiles can hold disks concurrently.
- **~30 s** to a running system under KVM. Check B1's 120 s budget is generous, which is right: it has to
  hold on the `low-ram` and `old-cpu` profiles too, and without KVM under TCG it would be far slower.

## Three failures it took to get here, all worth keeping

1. **A pipeline masked a failure.** The build step piped through `tail`, so the pipeline's exit status
   was `tail`'s and a *failing* `bootc-image-builder` scored as a *passing* step. `pipefail` is now the
   default shell in every workflow (D19).
2. **`ostree container commit` is obsolete** on this base and fails with *"Not in an ostree-based
   container environment"* — an error that does not point at its cause. Every tutorial written before
   2024 ends with that line (D20).
3. **The default root filesystem is too small.** 8.4 GB of layers into bib's default size fails with
   `min-free-space-percent '3%' would be exceeded`. Needs an explicit ≥20 GiB — which is also a fact
   about the **disk floor on a customer's machine** (D26).
